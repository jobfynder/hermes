fix(email-parsing): extract company/end-client, clean job description, preserve HTML line structure

Root cause: _strip_html() collapsed every block-level tag (<br>, <p>,
<div>, <tr>, <li>) to a single space instead of a newline, so a real
HTML email came out as one giant run-on line. Every line-anchored
field extractor downstream (job title, required skills, and now
company) silently stopped finding its labels on real mail -- only
plain-text or already-line-broken fixtures worked. Fixed by turning
block-level tags into newlines before the rest of the markup is
stripped, decoding HTML entities (&nbsp;/&lt;/&gt;/&amp; were showing
up literally in parsed text), and collapsing only horizontal
whitespace, not paragraph breaks.

Two gaps this surfaced, both confirmed against real production
drafts (Azure Integration Services Consultant / Abbott Labs, AWS
Connect Solutions Engineer / Oncor):

1. No field anywhere captured the job's actual client/company --
   "End Client: Abbott Labs" was sitting in the raw text with nowhere
   to go. Added company extraction (End Client/Client/Company/
   Employer labels) through the same path as location/rate/employment
   type: job_description_fields.py -> JobDescriptionStructuredData ->
   basic.py -> the job_requirement record -> field_provenance ->
   the review frontend -> Core's clientName on push (which was
   previously reading the recruiter's own signature company instead
   of the actual end client -- backwards for a job listing).

2. job_description stored the entire raw email verbatim, including
   the forwarded-message header block and the SEO-keyword/call-to-
   action footer many broadcast job boards append -- and it was never
   rendered in the review frontend at all (a gap in the original
   build, not a parser issue), so a well-parsed field looked "missing"
   to a reviewer. Added a conservative cleanup (strips only the top
   From:/Sent:/To:/Subject: block and known footer markers, not
   vendor-specific submission instructions, since a real JD can
   legitimately be a numbered list) and added the field to the
   detail page as a collapsible block with its own provenance chip.

Also fixes a title-extraction regression the newline change would
otherwise have introduced: when the real job title sits several
paragraphs past a forwarding preamble, existing extraction found
nothing. Added a same-email-subject fallback (only for the first
section, reusing the existing probable-title heuristic) so a title
is still found from the one place it's almost always spelled out
correctly.

New coverage: hermes-850-email-parsing-check.py gets a full forwarded-
posting fixture asserting title/company/location/description-cleanup
together; hermes-850-gmail-graph-provider-check.py gets a dedicated
line-structure/entity-decoding check. Full existing regression suite
verified green against a freshly reset schema.
